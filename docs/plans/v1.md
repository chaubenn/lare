## 0. What each surface is for

The decision that shapes everything else: **the desktop app exists because Whisper runs on
your machine.** Transcription stays local — it is not moving to the cloud.

| | Web + extension | Desktop app |
| --- | --- | --- |
| Passive practice capture | yes | yes |
| Feed, posts, profile, drafts | yes | yes |
| General / summary videos | browser recording | **native machine recording** |
| Mock interview — video | yes | yes |
| Mock interview — transcript | **no** | **local Whisper** |
| Mock interview — AI review | **no** | **yes** |

So a mock interview has two modes, and the user picks one explicitly:

- **Graded** — desktop app running. The extension captures the interview and streams the
  microphone to the app, which transcribes locally and grades it.
- **Ungraded** — no desktop app. The user turns off *Transcript & AI review*, and the
  interview runs entirely in the cloud: video only. Nothing is silently degraded; the
  toggle states plainly that it disables the AI review, because the transcript is what
  the review is built from.

That is the whole pitch for the app: **you can do everything on the web except be graded.**
The website is deliberately not a one-to-one clone.

### Who captures what

| Video | Captured by |
| --- | --- |
| Mock interview (screen + mic + camera) | **Chrome extension**, always |
| Summary video, demo video, any general video | **Desktop native recorder** *or* **browser recorder** — user's choice |

Native capture is the desktop's second justification: full screen and multi-display,
system audio, higher bitrates, and no tab sandbox. The browser recorder is the
no-install option and is available in both the extension and the website.

## 3. #32 — Make recording fast  *(the core of v1)*

Today the wait after you stop is **serial**, and every stage is blocked on the one before:

```
stop ─▶ write file ─▶ render ─▶ transcribe ─▶ upload ─▶ encode ─▶ ready
```

For a 45-minute interview that is minutes of staring at a progress bar. Loom feels instant
because almost none of that happens after you stop. Five changes, each removing one stage
from the post-stop path:

### 3.1 Create the video at record *start*
`bunny-create-upload` already returns TUS credentials. It is simply called ~45 minutes too
late. Move it to the start of the recording so the upload target exists before there are
any bytes.

### 3.2 Upload bytes *during* the recording
- **Extension / web**: `MediaRecorder` with a `timeslice` emits chunks every few seconds;
  each one is PATCHed to the TUS endpoint as it arrives, with OPFS as the spill buffer so a
  network stall never costs frames.
- **Desktop native**: the recorder already writes a growing MP4. A new `upload_to_bunny`
  variant tail-follows that file and PATCHes as it grows, reusing the TUS client already in
  `crates/lare-bunny`.

Two designs, picked by the P1 probe:

- **A — deferred-length TUS.** Send `Upload-Defer-Length: 1` at creation and the real
  `Upload-Length` with the final chunk. One hop, no intermediate storage.
- **B — parts to Bunny Storage, then Stream fetch.** Write numbered parts to a Storage
  zone during recording; on stop a new `bunny-finalize-recording` function exposes them as
  one object and hands Stream a single URL via `POST /library/{id}/videos/fetch`. More
  moving parts, but every call is documented and supported, and consecutive `MediaRecorder`
  webm chunks concatenate byte-wise (only the first carries the EBML header), so the
  stitch is a copy, not a re-mux.

Either way: **at stop, only the last few seconds are still in flight.** Upload completes
1–2 seconds after you stop, regardless of how long you recorded.

### 3.3 Do not render what was never edited
An instant demo currently goes through the full studio render even though nothing was
edited. Unedited video uploads raw and skips the render stage entirely. Only an actual trim
triggers a render — and that render streams into the uploader as it encodes rather than
waiting for the file to close.

### 3.4 Transcribe *during* the interview, not after
This is the largest single win, and keeping Whisper local is what makes it possible.

`crates/lare-transcribe` already exposes `transcribe_pcm(model, &[f32], ...)` — it takes a
raw PCM slice, not a file. So:

1. The extension's offscreen document taps the microphone through an `AudioWorklet`,
   downsamples to **16 kHz mono f32** — exactly the format `transcribe_pcm` wants — and
   sends it to the desktop app over the existing `ws://127.0.0.1:47831` socket as binary
   frames. That is 64 KB/s over loopback, which is nothing.
2. The desktop app transcribes in **rolling ~30 second windows as the audio arrives**,
   offsetting each window's timestamps, appending to `transcripts.segments` as it goes.
3. When the interview stops, the transcript is **already finished** — and the AI review
   can fire immediately instead of waiting for a decode and a full-length Whisper pass.

Two side effects worth having: `decode_to_pcm16k` (and its ffmpeg decode step) is bypassed
completely for interviews, and the user can be shown a **live transcript during the
interview** — something the web version structurally cannot do.

One required refactor: `transcribe_pcm` builds a fresh `WhisperContext` on every call. For
windowed use the context and state must be hoisted and reused, or the model gets reloaded
every 30 seconds.

If the desktop app disconnects mid-interview, the extension buffers audio and resumes on
reconnect. If it never comes back, the interview degrades to **ungraded** and says so
rather than failing.

### 3.5 Discard local video once it is safely up
Per #32, local video files are deleted once Bunny acknowledges the upload. The desktop app
keeps only what it needs: the studio project for edited takes, and nothing at all for
instant ones.

### The result

```
stop ─▶ flush last chunk ─▶ ready
```

Render, transcribe and upload all move off the post-stop path. What remains is Bunny's
encode, which is P2's job.

## 4. #31 — Chrome extension -> Side Panel

- `entrypoints/popup/` -> `entrypoints/sidepanel/`. Manifest gains `side_panel` and the
  `sidePanel`, `tabGroups`, `offscreen`, `tabCapture` permissions. Minimum Chrome stays
  116 (side panel needs 114, per-tab `setOptions` 116 — already met).
  `setPanelBehavior({ openPanelOnActionClick: true })` so the toolbar icon opens it.
- **Red recording outline** via `chrome.tabGroups` — detailed in §4.1 below.
- **Extension owns interview capture.** Screen, mic and camera all come from the extension
  now, via `chrome.tabCapture` in an offscreen document. Tab capture rather than
  `desktopCapture`: no picker, no prompt every time, and a LeetCode interview is a tab.
- **The desktop socket becomes optional, and changes purpose.** It no longer carries
  "please start recording". It carries the **microphone PCM stream** for local
  transcription (§3.4). Connected -> graded interview; not connected -> the sidebar offers
  the ungraded one.
- The panel is a real surface instead of a 400px popup: live session state, tracked
  problems, submissions, the transcript-and-AI toggle, and the publish entry point.

### 4.1 Red tab group while recording

`chrome.tabGroups` paints the recorded tab's strip in Chrome's own tab bar, so the "Lare
is recording this tab" signal survives the user tabbing away, minimising the window, or
forgetting the side panel is open. Requires the `tabGroups` permission alongside `tabs`
(API is Chrome 89+, well under our 116 floor).

**On record start**

```ts
const groupId = await chrome.tabs.group({ tabIds: [tabId] });
await chrome.tabGroups.update(groupId, {
  color: "red",              // fixed enum: grey blue red yellow green pink purple cyan orange
  title: "Lare • Recording",
  collapsed: false,
});
```

**On stop — restore, do not just ungroup.** This is the part that is easy to get wrong.
If the tab was already in one of the user's own groups, `chrome.tabs.ungroup()` throws
away *their* grouping, which is destructive and will read as a bug. So before grouping,
record the prior state and put it back afterwards:

| Tab was… | On start | On stop |
| --- | --- | --- |
| ungrouped | new group | `chrome.tabs.ungroup([tabId])` |
| in the user's group | move to new group, remember `groupId`, `title`, `color` | move back into the original group |

Since the recorded tab is a single LeetCode tab, the group will contain exactly one tab —
Chrome renders that as a coloured outline around the tab, which is the effect the
reference screenshot shows.

**Edge cases to handle rather than discover**

- User drags the tab out of the group mid-recording. Listen on `chrome.tabs.onUpdated` /
  `chrome.tabGroups.onRemoved` and re-apply once; if they do it again, respect it and stop
  fighting them. The on-page dot is still up, so the consent signal is not lost.
- Tab moves to another window — groups are per-window, but Chrome carries the group with
  the tab, so nothing to do.
- Tab is closed mid-recording — stop the recording and finalise the upload with what has
  already streamed (§3.2 means that is nearly everything).
- Incognito — `tabGroups` is unavailable unless the extension is allowed in incognito.
  Degrade to the on-page dot only; do not fail the recording.
- Group state must be re-applied on service-worker restart, since MV3 workers are killed
  freely. It goes in the same persisted state the interview session already uses.

**It is decoration, not consent.** A tab group is cosmetic and the user can remove it at
any time, so it never replaces the on-page red dot, which is what `docs/privacy.md`
commits to ("it never records without one"). The tab group is an additional, more visible
signal — not a substitute.

- **Remove the Recordings tab** — delete `features/recordings/`, its nav entry and route.

  `src-tauri/Cargo.toml`, `apps/extension/package.json`. Tag once QA on `dev` passes.

## 7. #36 — Move everything to the cloud  *(scope corrected)*

Originally "investigate cloud speech-to-text". **That is now explicitly rejected** —
local Whisper is the desktop app's reason to exist, so `crates/lare-transcribe`,
`publish-models.yml` and the whisper-models release all stay exactly where they are.

What still moves to the cloud: video storage and delivery (§3), which is what actually
caused the local bloat.

Migration `0015_v1.sql`:
- `sessions.graded boolean not null default true` — was this interview transcribed and
  reviewed, or was it the ungraded cloud-only path? Drives what the session and post pages
  offer, and stops an ungraded interview from looking like a failed graded one.
- `videos.capture_source` enum `('desktop','extension','web')` — needed to diagnose
  quality complaints, since the three paths produce genuinely different files.
- `transcripts.segments` gains incremental upsert support for §3.4's rolling windows.

## 8. #37 — Codebase cleanup  *(last, deliberately)*

A repo-wide move done early would conflict with every other branch of work.

- `crates/cap/` -> `crates/vendor/cap/` — it is vendored upstream (`UPSTREAM_COMMIT`,
  `sync-cap.sh`); burying it makes the five first-party `lare-*` crates visible.
- `apps/desktop/src/features/` — fold `recording/` + `recordings/` + `studio/` into one
  `media/` now that Recordings is gone, and `drafts/` + `posts/` into `publishing/`.
- `packages/shared/src/` is a flat bag of 12 unrelated modules; group into `session/`,
  `leetcode/`, `format/`, `media/`.
- **AI/agent files.** `.hallmark/` moves to `.ai/`. `.cursor/` does **not** — Cursor only
  reads rules and skills from `.cursor/` at the repo root, and moving it silently breaks
  them. `AGENTS.md` / `CLAUDE.md` stay at the root for the same reason: they are
  path-sensitive discovery points. The ticket pre-authorises the risk ("if this affects
  agents picking up the skills, just disregard"), so `.ai/README.md` becomes the index
  pointing at the ones that must stay put.

One commit per move, via `git mv`, so the diff reads as renames.

## 10. Risks

- **§3 design A may not be available.** Design B is the fallback; more code, no more risk.
- **Bunny encode latency is not fixable in code** — only P2 addresses it.
- **Windowed Whisper can cut words at window edges.** Mitigated with ~2s overlap between
  windows and de-duplication on the seam; worth QA attention specifically.
- **Old desktop builds keep talking to the old protocol.** The extension has to tolerate a
  stale desktop app being open and treat it as "not available for grading" rather than
  erroring.
- **#37 touches almost every file** — hence last.
