# Lare v1 (Alpha) — delivery plan

Covers issues #31 #32 #33 #34 #35 #36 #37. Target version **v1.0.0**.

Ordering is deliberate: #35 first (it makes the dev branch usable for QA), then the
architecture change (#32 -> #31 -> #33 -> #34), then #37 last — a repo-wide file move
done early would conflict with every other branch of work.

## 0. Prerequisites — things only you can do

Nothing below blocks #35. Everything else has at least one item here in front of it.

### P1 — Bunny Stream API key (blocks #32, #36)
A **library-scoped** Stream key for library `743884` (Stream > Library > API), not the
account-wide key. Needed for two things:

1. A one-off probe of whether `https://video.bunnycdn.com/tusupload` accepts the TUS
   `creation-defer-length` extension (`Upload-Defer-Length: 1`). Bunny does not document
   it either way, and the answer picks between design A and design B in §2. This is a
   ~10 minute experiment and it decides the shape of the whole upload path.
2. Verifying the transcribe endpoint end to end (§6).

The key currently wired into the repo is full-account scope — rotate it while you are in
there, and give me only the library-scoped one.

### P2 — Bunny library settings (blocks #32)
Two toggles in the Stream library dashboard, both of which cost money, so they are your
call and not mine:

| Setting | Effect | Cost |
| --- | --- | --- |
| **Encoding tier: Premium + JIT encoding** | Playback starts without waiting for the full transcode. This is the single biggest win for "no wait times". | Premium encoding tier |
| **Allow Early Play** | Lets a video play while it is still encoding. Cheaper half-measure if you do not want Premium. | Free |

Without at least one of these, uploads become instant but Bunny's *encode* wait stays,
and the perceived delay in #32 is only half fixed. Tell me which one you want and I will
wire the UI to match (Early Play needs a "still processing" player state; JIT does not).

### P3 — Transcription decision (blocks #36)
Bunny Stream has a built-in Transcribe endpoint
(`POST /library/{id}/videos/{guid}/transcribe`), powered by Whisper, billed at
**$0.10 per language-minute**. It is the cheapest path to "move everything to the cloud"
because it needs no new vendor, no new secret, and `supabase/functions/bunny-webhook`
*already* handles Bunny status `9 = CaptionsGenerated` — the hook is sitting there unused.

I recommend it over OpenAI/Deepgram/AssemblyAI for exactly that reason. But at $0.10/min a
45-minute mock interview costs $4.50 to transcribe, so confirm before I build on it.
Alternative if that is too steep: OpenAI `gpt-4o-transcribe` (~$0.006/min) using the
OpenAI key you already have for `ai-review` — cheaper, but it is a second pipeline to
maintain and the audio has to be pulled back out of Bunny first.

### P4 — Two product decisions (blocks #31, #33, #34)
These change what gets built, not just how:

1. **Does the desktop app keep recording at all?** #31 moves mock-interview capture into
   the extension, and #33 says nothing needs to be local any more. My read: the extension
   owns LeetCode capture (tab + mic + optional camera via `chrome.tabCapture` in an
   offscreen document), and the desktop app keeps *general* screen recording for demo
   videos that are not a LeetCode tab. The alternative is retiring the Rust recording
   stack entirely, which is a much bigger deletion — and you would still be shipping DMGs
   per #35, so the app has to justify its existence some other way. Confirm which.
2. **Tab capture vs. screen capture for interviews.** `chrome.tabCapture` records only the
   LeetCode tab — no permission prompt, no picker, much better UX. Screen capture via
   `chrome.desktopCapture` records everything but prompts every time. Tab capture is the
   right default for a LeetCode mock interview; say so if you disagree.

### P5 — Supabase migration (no MCP needed)
You said no MCP, so every schema change lands as one reviewable file:
`supabase/migrations/0015_v1.sql`. You run it. I will keep it idempotent
(`if not exists` / `or replace`) so a partial run can be re-applied safely, and I will
list in the PR description exactly what it touches.

### P6 — Edge Function deploys are manual
Vercel auto-deploys the web app on push, but the Supabase Edge Functions do not. Anything
in §2 and §6 needs `supabase functions deploy` from your machine after merge, plus
`BUNNY_STREAM_API_KEY` / `BUNNY_TOKEN_KEY` / `BUNNY_STREAM_READONLY_KEY` present as
function secrets.

## 1. #35 — Maintenance, architecture, testing environment  *(unblocked — doing now)*

**Dev branch + CI split.** Today `ci.yml` runs on `push: [main]` and on every
`pull_request`, and the Rust matrix alone is capped at 90 minutes. So a push to `dev`
currently gets *no* CI at all, and a PR to main gets all of it.

- **Fast lane** on push to `dev`: biome, `tsc`, `@lare/shared` unit tests, web build.
  ~3 minutes. No Rust matrix, no Playwright.
- **Full lane** unchanged on PRs targeting `main` and pushes to `main`: everything,
  including the Rust matrix and the extension e2e.

That matches the ticket exactly — commit freely to dev, pay the 40 minutes once at the PR.

**Release process file.** New `docs/releasing.md`; the "Release process" section moves out
of the README and gains the missing pieces (the version-bump checklist across all four
files, what the updater key is for, how to recover a failed publish).

**Release assets.** `release.yml` already has a trim step that keeps the four stable
installers plus `latest.json`. The ticket asks for "source code" too — that is
automatic on GitHub releases and cannot be removed, so nothing to do. One correction to
the ticket: the versioned `*_x64-setup.exe` / `*.app.tar.gz` artifacts *look* redundant
but `latest.json` points at them, and deleting them breaks self-update for every installed
app. They stay; I will document why in `docs/releasing.md` so nobody trims them later.

**README.** Brand logo (`brand/wordmark.png`), shields (CI status, release, license,
platform), tightened intro, install table, link block to the docs.

**Privacy/compliance.** `docs/privacy.md` is materially wrong after #31/#32/#36: it says
raw recordings stay on the device and that transcription is local. Both stop being true.
It gets rewritten alongside those changes, not before.

## 2. #32 — Realtime upload  *(blocked on P1, P2)*

Today: record -> write MP4 to disk -> render -> *then* create the Bunny video and start
TUS. Upload cannot begin until recording is completely finished, which is the wait.

Fix, in order:

1. **Create the Bunny video at record start**, not at stop. `bunny-create-upload` already
   returns TUS credentials; it just gets called ~40 minutes too late.
2. **Upload while recording.** Two designs, picked by the P1 probe:
   - **A — deferred-length TUS** (if Bunny accepts `Upload-Defer-Length: 1`): PATCH chunks
     as MediaRecorder emits them, send `Upload-Length` on the final chunk. Clean, one hop,
     no extra storage. This is what Loom effectively does.
   - **B — parts to Bunny Storage, then Stream fetch** (if it does not): write numbered
     parts to a Storage zone during recording, then a new `bunny-finalize-recording` edge
     function stitches them and hands Stream a single URL via
     `POST /library/{id}/videos/fetch`. More moving parts, but every call is documented
     and supported. Bytes still leave the machine during the recording, which is the point.
3. **Discard local video.** Once the upload is acknowledged, delete the local artifacts.
   Combined with #31 this is what removes the disk bloat the ticket complains about.
4. **Kill the encode wait** via P2.

Chunk transport lives in the extension's offscreen document (MediaRecorder + OPFS as the
spill buffer), so it is shared by the extension and — if you keep it — the desktop app,
which can reuse the existing Rust TUS client in `crates/lare-bunny` for design A.

## 3. #31 — Chrome extension -> Side Panel  *(blocked on P4; depends on §2)*

- `entrypoints/popup/` -> `entrypoints/sidepanel/`. Manifest gains `side_panel`,
  and permissions `sidePanel`, `tabGroups`, `offscreen`, `tabCapture`. Minimum Chrome
  version stays 116 (side panel needs 114, per-tab `setOptions` needs 116 — already met).
  `chrome.sidePanel.setPanelBehavior({ openPanelOnActionClick: true })` so the toolbar
  icon opens the panel.
- **Red recording outline** via `chrome.tabGroups`: on record start, group the recorded
  tab with `color: "red"`, title `Lare • Recording`; ungroup on stop. Keeps the existing
  on-page red dot as the in-page signal (it is also a consent requirement — see privacy).
- **Cut the desktop dependency.** Delete `src/ws.ts` and every `DesktopClient` call in
  `entrypoints/background.ts`. `startInterview` stops requiring a live socket; capture
  happens in an offscreen document and uploads straight to Bunny by §2. Auth already
  works standalone (`src/auth.ts` does OAuth + OTP against Supabase directly) — nothing
  to add there.
- The panel is a real surface now rather than a 400px popup, so it gets the full layout
  from the mock: live session state, tracked problems, submissions, and the publish entry
  point.

`packages/shared/src/protocol.ts` and the desktop `ws_server.rs` only get deleted if P4.1
says the desktop stops recording; otherwise they stay for the desktop's own path.

## 4. #33 — Tauri sidebar layout on the web  *(depends on §3)*

- New `apps/web/components/app-shell/` mirroring `apps/desktop/src/features/shell/` —
  same nav items, same active-pill motion, same `@lare/ui` primitives.
- **Applied at `md:` and up, and only when logged in.** Below `md`, and for logged-out
  visitors, the current header + bottom tab bar stays exactly as it is. The ticket is
  explicit that the mobile experience is not to be sacrificed.
- Logo in the sidebar top-left navigates to the landing page (web only).
- Web is missing routes the desktop has: **drafts** and **sessions** have to be built
  from scratch in Next.js. That is the bulk of this ticket, not the chrome itself.
  Recordings is not among them — #34 deletes it.

## 5. #34 — Recordings tab, studio, draft flow, sessions  *(depends on §4)*

- **Remove the Recordings tab**: delete `features/recordings/`, its nav entry and route.
- **Keep all of the studio/trimming work** (`features/studio/`, `crates/cap/editor`,
  `cap-export`) and re-point it: trimming becomes a step reachable from *any* video —
  instant, full interview, or summary clip — instead of a tab of local files. Route
  becomes `/studio/:videoId` against a cloud video rather than `/studio/:recordingId`
  against a local project.
- **Draft flow -> a real stepper.** Today `DraftEditorPage.tsx` is one 327-line page with
  every control at once. Replacing it with: Problems -> Media (record / attach / trim) ->
  Details -> Extras (AI insights, OG card, visibility) -> Review & publish. Each step
  validates before advancing; the draft is saved continuously so leaving never loses work.
- **Sessions tab gets richer.** It is owner-only, so there is no reason to hold back:
  full timeline, per-problem submissions with verdicts and percentiles, the code edit
  timeline, transcript and the AI review inline.
- **Version -> 1.0.0** across `apps/desktop/package.json`,
  `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/Cargo.toml`,
  `apps/extension/package.json`. Tag `v1.0.0` once QA on dev passes.

## 6. #36 — Move everything to the cloud  *(blocked on P3)*

The umbrella ticket. The only piece not already covered by §2–§5 is speech-to-text:

- Delete `crates/lare-transcribe` (whisper.cpp, whisper-rs, the Metal feature, the ~466 MB
  model download) and `.github/workflows/publish-models.yml` plus the `whisper-models`
  release. This also meaningfully shrinks the desktop bundle and the Rust CI matrix.
- Replace with Bunny transcribe (or OpenAI — P3), triggered from `bunny-webhook` when a
  video reaches `status 3` (Finished). The webhook already parses `9 = CaptionsGenerated`;
  on that event, pull the VTT and upsert `transcripts.segments` in the shape the AI review
  and `apps/web/components/transcript.tsx` already expect. No schema change needed for
  this part — `transcripts.model` just stops saying `whisper.cpp`.

## 7. #37 — Codebase cleanup  *(last, deliberately)*

Proposed moves, kept to naming and grouping so review stays tractable:

- `crates/cap/` -> `crates/vendor/cap/` — it is vendored upstream (`UPSTREAM_COMMIT`,
  `sync-cap.sh`), and burying it makes the five first-party `lare-*` crates visible.
- `apps/desktop/src/features/` — fold `recording/` + `recordings/` + `studio/` into one
  `media/` now that Recordings is gone, and `drafts/` + `posts/` into `publishing/`.
- `packages/shared/src/` is a flat bag of 12 unrelated modules; group into
  `session/`, `leetcode/`, `format/`, `media/`.
- **AI/agent files.** `.hallmark/` and the repo's `AGENTS.md` / `CLAUDE.md` move under
  `.ai/`. `.cursor/` does **not** — Cursor only reads rules and skills from `.cursor/` at
  the repo root, and moving it silently breaks them. Same for `AGENTS.md`/`CLAUDE.md`,
  which are path-sensitive by design. The ticket pre-authorises this ("if this affects
  agents picking up the skills, just disregard"), so: `.ai/README.md` becomes the single
  index that points at the ones that must stay where they are.

Done as one commit per move with `git mv` so the diff reads as renames, not rewrites.

## Risks

- **§2 design A may not be available.** The P1 probe is the first thing I run once I have
  the key; design B is the fallback and is strictly more work but no more risk.
- **Bunny encode latency is not something code can fix** — only P2 addresses it. If both
  toggles are declined, #32 will land as "upload is instant, playback still waits", and
  that should be a known outcome rather than a surprise.
- **§3 removes the desktop app from the interview path.** Every existing installed client
  keeps talking to `ws://127.0.0.1:47831` until it self-updates, so the extension has to
  tolerate an old desktop app being open and ignore it, not error on it.
- **§7 touches almost every file.** It goes last, in its own PR, after everything else has
  been QA'd on dev.
